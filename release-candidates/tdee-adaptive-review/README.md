# Adaptive TDEE review candidate: not an active feature

This package is an **inert engineering candidate**, not a deployed service, new environment, clinically reviewed policy, native UI connection or authorization to change targets. Production Progress v15 remains observational. Its recommendation actions still reject. Nothing in this directory is imported by the current application or Edge entrypoint.

## Implemented locally

`proposal.ts` implements a testable, non-actionable draft calculation and input barriers. `ADAPTIVE_RELEASE_STATE` is immutable OFF with no reviewed policy. Every result, including a successful engineering draft, has `actionable:false`; it cannot be submitted to the acceptance controller as a reviewed proposal.

- No numerical adjustment policy is silently supplied. Step size, fractional cap, cumulative cap, cadence, granularity, intake range, snapshot freshness and weight freshness must be explicit review inputs. The test choices (such as 100 kcal, 5% and seven days) are **synthetic engineering fixtures, not clinical recommendations or production defaults**.
- A coherent, enriched source contract, validated model/eligibility, explicit complete-day attestation workflow and serialized-source revision are required. Today's low-confidence/unverified observation does not satisfy this new contract. The code does not manufacture those attestations from meal counts, profile fields or an enable flag.
- A server-owned anchor binds the expenditure reference and original accepted intake. Proposed target is anchored intake plus the change in expenditure, not another deficit subtracted from an already reduced goal. Current goal/version and accumulated changes must match the anchor's receipt chain.
- No calorie reduction is proposed. Existing 1,200/1,500 product references are preserved as lower boundaries, never described as universally safe. The current weight must match a dated, source-attributed, latest non-conflicting normalized weight from the coherent evidence; a stale profile value cannot override it. A reached/contradictory weight goal, anchor inconsistent with loss/gain/maintenance intent, unclear eligibility or an invalid existing target requires review, not substitution.
- Per-step and accumulated increases are bounded; positive acceptance history requires a real last-acceptance date. Midnight/expiry invalidates the old source. Overlapping sensitivity ranges block a directional draft but are **not interpreted as statistical confidence intervals**.
- Macro allocation is an explicit candidate strategy preserving accepted energy proportions, with whole-gram rounding, the existing energy tolerance and unchanged fiber. Zero is preserved. That strategy still requires qualified review before activation.

`acceptanceController.ts` implements the headless request/recovery state machine with dependency contracts, not real network or storage bindings. It takes a trusted persisted reviewed proposal, never target numbers from the request. Preparation is durable before transmission; unknown outcomes retain the exact request; recovery is read-only and retries are explicit. Authoritative receipts can reconcile a committed operation after the policy is disabled. Account/focus cancellation never claims to undo a possible server commit. Definitive rejections have an explicit acknowledgment path, reconciled against the authoritative receipt before atomically clearing only that rejected journal. A contradictory `not_found` response never authorizes resend. Committed receipts preserve exact goal CAS, distinguish current/superseded, and always require a fresh active-goal read.

Its future bindings must provide an authenticated, transactional acceptance endpoint, an owner-scoped durable journal, authoritative receipts and verified safety capability. Mocks used in tests do not provide those production guarantees. Do not bind it to the manual goal RPC, direct goal updates, preview acceptance or the old cron.

## Not implemented or verified

1. No qualified approval of the exact policy, algorithm, eligible population or macro strategy. Citations describe evidence and limits, not approval of this app.
2. No actual enriched snapshot exposing coherent profile/goal CAS plus policy/eligibility/completeness/anchor revisions.
3. No production writer barrier or proven serializable acceptance transaction. The local `sourceBarrierCandidate.sql` now implements private revisions, immediate owner-workset collection with a deferred globally ordered flush, and a U→G→owner-fence→revision helper, but remains uninstalled and untested against real source interleavings. It fails preflight while API roles retain TRUNCATE. The separate permission-only change was explicitly confirmed and applied on 2026-11-13: 24 TRUNCATE combinations removed, all other ACL entries/CRUD/RLS preserved. That prerequisite does not install or validate the barrier. Neither candidate grants an acceptance API or represents a proven barrier. Existing production food/weight/settings direct writes can still race a hash recheck.
4. No persistent reviewed-proposal/anchor/receipt registry or native encrypted-journal binding for this operation.
5. No proposal screen, active accept button, automatic review/acceptance, scheduled activation or native E2E. No account targets were changed; the separately authorized inactive subscription fixture was transient and fully rolled back.

See `EVIDENCE_AND_GATES.md`, `ACCEPTANCE_CONTRACT.md` and `sourceBarrierReview.md` for the evidence, current production facts and exact missing capabilities. Those capabilities must be independently reviewed and tested before any write-capable binding. Enabling a boolean, passing unit tests or receiving general user approval does not establish them.

## Verification scope

Tests execute the actual candidate code with synthetic inputs and injected in-memory dependencies. They check software decisions, actor/recovery behavior and failure handling. They do not validate physiological estimates or prove PostgreSQL concurrency, clinical safety, app installation, native storage or account E2E. No new test environment, account, persistent fixture data, build or TestFlight distribution is created by these checks. Authorized SQL rehearsals in the existing DB used private synthetic workset/revision rows and a separate inactive subscription fixture with forced full rollback. The synchronized private-core test passed with two actual sessions; the subscription source callback passed 11 checks with exact catalog restoration. Neither proves the other eight sources, cascades, normal committed writer concurrency or authenticated app recovery.
