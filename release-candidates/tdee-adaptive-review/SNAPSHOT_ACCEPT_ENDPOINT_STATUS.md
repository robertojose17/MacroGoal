# Adaptive acceptance endpoint source
Prepared OFF only. No deployment or test execution. Existing runner restriction remains.
POST progress-intelligence?mode=adaptive-accept-v1 accepts JSON directly with exactly ownerId, requestId, proposalId, proposalDigest. Content-Type must be application/json; body limit 2048 bytes. No action, p_request, target, evidence or enable flags.
HTTP 200 returns the existing terminal adaptive-receipt-v1 receipt directly (committed or rejected). Never not_found. Fields are validated and reconstructed, not passed through with arbitrary extras.
HTTP 409 returns {reason:'reconciliation_required',receipt:null,mayHaveWritten:true} for unknown acceptance outcomes. Do not automatically retry acceptance: reconcile through the existing receipt RPC with the same identity.
Pre-acceptance failures use 400/401/403/503 with {reason,receipt:null,mayHaveWritten:false}. OFF is 503 safety_review_required before any client/auth/read/authority call. Existing independent receipt recovery remains available; this OFF endpoint does not attempt replay.
When enabled in a separately reviewed release, authentication uses auth.getUser and compares immutable owner. The own-bearer receipt read happens first. A terminal replay skips preflight and acceptance. Only not_found proceeds through existing scoped tester refresh, then immediately the own-bearer acceptance RPC. No service key is read, no entitlement TTL is extended by this code, and no arbitrary account can nominate itself as a tester. SQL remains authoritative for current access and all acceptance guards.
The dispatcher's old routes remain unchanged; mixed modes fail closed and cannot forward authorization to legacy. Same exact web-origin allowlist, native no-Origin support and private no-store headers apply to successes and failures.
Tests: ten prepared cases cover real OFF zero clients, overposting, receipt sanitation, uncertainty, HTTP rejection, own RPC credentials, managed/unmanaged preflight, preflight failures, dispatcher selection and failure distinctions. NOT RUN. Positive enabled runtime sequence, replay and simultaneous changes still require authorized execution and application verification. No enabled fake release flags are introduced for tests.

The runtime's mayHaveWritten:false alongside a terminal receipt is an internal outcome marker, not a claim that a committed goal was untouched. That marker is not sent with HTTP 200: the client receives the authoritative receipt directly. Positive enabled runtime replay/order tests are intentionally pending; immutable OFF is not bypassed in tests.
