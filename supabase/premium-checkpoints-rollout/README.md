# Premium checkpoint rollout candidate

Inactive source only. No SQL has been applied, Edge function deployed, or client transport enabled. Main is unchanged. This directory is outside automatic migrations and functions deployment paths.

## Exact proposed scope

- 10-private-checkpoints.CANDIDATE.sql: one private checkpoint_events table, indexes and public.record_private_checkpoint_v1(uuid,jsonb). New schema access revoked from PUBLIC/anon/authenticated, table RLS enabled and forced, no ordinary read policy. Service can read for owner reconciliation and execute insertion RPC; no direct table write grant. RPC validates service JWT role, uses empty search_path, immutable JSONB equality for duplicate ACK versus conflict, server received time and bounded per-user rate.
- edge/protocol.ts: copied closed client schema. The parity regression must pass whenever either side changes. No actor, health fields, receipt, purchase token, free text or payment-confirmed event is accepted.
- edge/index.ts: candidate premium-checkpoint JWT endpoint. Existing pinned Supabase dependency 2.83.0; existing server environment only. It derives user ID with getUser, caps streaming request at 8 KiB, returns accepted/duplicate/conflict and retryable statuses. No read API. No payload/token logging.
- reconcileObservedPayments.ts: pure owner/service-only read-only reconciliation. Caller must supply the complete server-origin revenuecat_events mirror after a reviewed authentication boundary, including all duplicate variants for relevant vendor IDs/transaction keys, private checkpoint rows, and a server-authorized verifiedAuthUserIds snapshot/resolver from auth.users. The raw provider app_user_id UUID is mapped through that verified set; nullable normalized revenuecat_events.user_id is not required. Never construct the verified set from client checkpoint claims. Do not expose this output to ordinary users, use client-supplied provider rows, or prefilter stores/environments before reconciliation. Owner Sheet integration and paginated snapshot acquisition are still pending.
- 20-postflight.READONLY.sql: metadata checks for grants, RLS, function ownership/search_path and cascading foreign keys. This script was prepared, not run against nonexistent candidate objects.

## Measurement and payment limits

22 premium route calls across 18 production entrypoint files are instrumented, plus the subscription screen and hook documentation. There are 16 inline prompt observers. Automatic redirects are entry events without fabricated impressions. Manual and autoStart converge at SDK purchase invocation. Restore and client SDK results never establish a new paid sale. Legacy analytics remain separate.

Provider normalization uses raw_event.event, event_data.event, raw_event, event_data in that order. Only actual positive vendor local-currency prices and qualifying purchase event types are considered; no amount_usd fallback. Vendor IDs and store/environment/transaction keys deduplicate. All duplicate variants are inspected before positive-price/trial qualification. Conflicting financial variants are excluded from payments and placed in a separate quarantine with no selected amount or product; ambiguity of source attribution is a separate status on otherwise valid financial facts. Exact actor/product/transaction lookup spans all trusted keys; optional client dimensions only validate agreement. A consistent server-ingested attempt with the same flow/attempt/product and provider purchase time within -2/+30 minutes of server receipt is required. Attempt server receipt must also be no later than result server receipt. Missing, replayed, offline and deferred matches remain unattributed. Multiple qualifying attempts are ambiguous. This is bounded client attribution, not proof of visual exposure.

Report provider purchases observed and matched with coverage. Mirror completeness is unverified. Do not call these cash, MRR, or definitive new subscribers; first paid remains unknown. Quarantined transaction keys are already excluded from payments and financial totals. Returned coverage counts include inspected provider rows, observed/matched/unmapped payments, conflicting vendor IDs/transaction keys and unmatched claims; these categories are not additive partitions. Refunds/cancellations are not netted by this minimal purchase-observation report. Production and sandbox must remain separately labeled in owner outputs.

## Deletion, retention and existing privacy text

Read-only metadata verified auth.users(id) and public.users(id) primary keys and the existing public.users -> auth.users ON DELETE CASCADE relationship. The current app/delete-account.tsx deletes public profile rows and signs out; it does not directly delete Auth accounts. The candidate therefore uses BOTH auth.users and public.users cascading FKs for the new checkpoint table. Successful deletion through either route removes new checkpoints and prevents reinsertion without both records. This deliberately gates checkpoint capture on an existing public profile: valid Auth with no profile receives HTTP 409 profile_unavailable, including the profile-FK race, rather than being mislabeled as an invalid JWT. Missing Auth receives 401 account_unavailable; invalid JWT receives 401 unauthorized. No automatic profile creation or purchase blocking is introduced. Existing account deletion errors/authority guards are outside this change; do not bypass or modify them. No existing user records are altered by this package.

Coverage limitation: parent read-only audit found 141 Auth accounts without profiles (112 with prior sign-in). Historical counts of 38 paywall mounts and 10 manual CTAs do not establish that their profiles were missing at those event times. These are audit account counts, not measured rejected checkpoint counts or a current conversion denominator. No rejected user-linked checkpoint is stored, so exact lost-event coverage remains unknown. Excluded accounts must be disclosed before activation; this implementation does not claim all-user coverage. Choosing another deletion mechanism or account repair requires a separate decision.

No separate retention scheduler is introduced. Account-linked raw checkpoints persist while the account/profile exists until an owner-approved retention period is chosen; review that period before activation. Existing provider retention is unchanged. IDs are pseudonymous, not anonymous. No ordinary user can browse checkpoint data.

Existing en/es privacyPolicy.collectList mentions usage data and analytics, and howWeUseDesc describes improving the app experience. It does not explicitly describe account-linked premium funnel attribution. Whether existing disclosure is sufficient remains owner review; no legal or privacy text was edited.
